## 一、严重（必须修，建议今晚）

### S1 · LLM 失败被计成"已分析"，报告说谎且退出码 0 —— **两条路径都说谎**
**发现方**：super agent ｜ **复核**：工程交付伙伴（实读代码）

**路径 A · pipeline（`report_generator.py`）**
```python
成功分支 :1070-1074 → {section, tier, takeaway}    # 无 analyzed 键
异常分支 :1079-1087 → {section, tier, takeaway}    # 也无
汇总     :1784      → r.get("analyzed", True)      # 缺键默认 True
```
全仓只有两处显式写 `"analyzed": False`（:988 / :1724）。

**路径 B · 日报（`assistant_daily.py`）**
```python
for tag in ("extract", "extract-retry", "extract-reasoning"):
    try: ...
    except Exception as e:
        logger.warning(...); continue      # 三档全失败后无任何标记
return {"facts": facts, "noise_ids": noise, **narr}   # 结构里没有 llm_failed
```
三档重试全挂 → `facts=[]` → 渲染成"无新内容" → 汇总"有信息 0 / 无信息 0"。

**后果**：模型故障时，pipeline 显示"分析失败文本但计入已分析"，日报显示"无新内容"。
**两种表现都不是失败，一场模型故障是无声的。**

**修法（必须覆盖两条路径）**：
- A：异常分支 `"analyzed": False` + `"llm_failed": True`；汇总改 `is True`；失败数>0 时头部警告 + exit 非 0
- B：给 results 加 `llm_failed` 计数，写进日志与报告头部

### S2 · X 采集失败与"无 X 帖"不可区分
**发现方**：super agent ｜ **复核**：工程交付伙伴（实读代码）

```python
x_sources.py:105-118
  if not root:            return []   # 配置缺失
  if not path.exists():   return []   # 文件不存在（未采集）
  except Exception:       return []   # 坏 JSON
  if not isinstance(...): return []   # 结构异常
```

四个分支全部返回 `[]`，调用方无法区分"今天没采到"与"今天确实没帖"。

**与 11-24 事故的关系**：**这是同一机制的另一半。** 11-24 的 X 数据其实有 1184 条，
只是没进日报（已修）。但如果哪天 X 采集真的失败了，日报表现得一模一样——
"没采到"和"没帖"在报告里都是"无新增量"。

> **⚠️ 更正（2026-11-25，工程交付伙伴自查）**：本文档初版写的「11-24 有 22 只美股雪球
> 0 帖、被 `if not kept: return empty` 整只跳过」**是错的**。实测 11-24 全部 **23 只美股
> 雪球都有帖**（NVDA 110 / TSLA 110 / BABA 110 / PDD 72 / TSM 62…）。
>
> 错误来源：对比脚本用 `crawl_snapshots.stock_code`（格式 `PDD.US`）去查 X 文件名
> （格式 `PDD`）的 key，`sk.get("PDD")` 恒为 0，凭空空造出"22 只雪球空"。
>
> **真实机制**：第一层 bug（`if not kept: return empty`）在 11-24 **没有触发**；
> X 内容丢失全部由**第二层**（渲染时 `by_id` 只索引雪球帖）造成。
> 修复因两层都补了，结果正确；但初版的**影响面描述与因果链是错的**。

**修法**：X enabled 且 is_us 时，若当日文件不存在 → 不视为"无帖"，写
「X 源缺失（采集未落盘）」并告警；文件存在但 `posts=[]` 才算真无帖。

### H9【高】X 历史帖污染（与缓存错配同批）
**发现方**：FA ｜ **修正**：工程交付伙伴（初判为"当前不成立"，错误）

**实测 11-24（走 `as_prompt_posts` 现算，不是读落盘文件）**：
```
清洗后 1068 条 | is_fresh=True 444 (41%) / False 624 (58%)
days_ago: min=0.7  中位=3.8  max=3339.0（2017 年的帖）
days_ago<=1.0: 399 条
```

**为什么初判错了**：落盘 JSON 里**没有** `is_fresh` 字段（0/23 文件带此字段），
它是 `to_post_dict()` 现算的。用 `p.get('is_fresh', True)` 统计 → 永远得到 100%。
**这与 S1 的 `r.get("analyzed", True)` 是同一个模式：默认值把"不知道"盖成了"正常"。**

**实际风险（不是误判 deep，是反向）**：
一只票雪球 0 新增、X 只有几条 9 年前的帖，也会被判 deep 去调 LLM。

**修法三个约束**：
1. 阈值用 `days_ago <= 1.0`（与雪球当日口径对齐），**不用 `is_fresh`**
   —— `FRESH_DAYS=1.5`，is_fresh 过滤后仍有 45 条是 1~1.5 天前的
2. **过滤只能在一处做**：`analyze_stock` 与 `by_id` 补索引必须用**同一个过滤后列表**，
   否则 `X_ID_BASE + i` 立即错位——即 P2 缓存错配的同类错误，换成"过滤"触发
3. 抽公用函数：`is_today(p, date_str)` / `new_today(xp, date_str)`，雪球/X/监控共用

**不可做**：改成"强制插入 posts"——会破 `uq_posts_stock_dedup`。

### H7 待主人拍板的三个选项

**(a)** X-only → STD（不是 DEEP）
**(b)** DEEP 仅当 X 帖数 ≥N 且互动量 ≥M
**(c)** 保持 DEEP，但小节标题强制标【未证实·X 源】

(super agent 倾向 (a)+标题标注：既不把传闻拉到最贵档，也不让它隐形；(a) 与 (c) 可叠加)

### 陷阱：加第二次 X 采集必须**先改 ingest 合并**，否则丢数据

`x_ingest.py:292-302` 帖子文件是**整份覆盖**（`payload` 只含本次采集，不读旧文件）：

```python
payload = {"ticker":..., "date":..., "status":..., "slices":..., "posts": posts}
_atomic_write_json(root / date_str / f"{ticker}.json", payload)   # 覆盖
```

直接加 18:00 采集 = 用新一批换掉旧一批 → top 标签下的旧帖、跌出 live 前 25 的帖永久丢失。

**正确顺序（三步不可拆）**：
1. 改 `ingest` 为合并：读旧文件 + 按 `tweet_id` 并集 + 按 `collected_at` 重算 status
2. 缓存键改为内容指纹（含顺序敏感 hash），否则重跑必错配
3. 最后才加 18:00 采集

**另需定义**：`_config_keep_days()` 已存在（`x_source.keep_days`），改合并时要明确"合并后超保留期的旧帖是留下还是清掉"，否则磁盘会持续增长。

### 为什么 H1 与 M2 必须成组

- 只修 H1（缓存指纹）不修 M2：修了个**永不触发的防护**（现在 X 每天只采一次，数据很少中途变化）
- 只修 M2（加第二次采集）不修 H1：缓存错配从"偶发"变成**每日常态**（两次采集数据必然变，任何重跑都命中旧缓存）

## 七、本轮方法教训（留档）

1. **grep 关键词 ≠ 语法级依赖判断**。`getLogger("x")` 与 `import x` 在 grep 眼里一样。
2. **"stash 后仍失败"只证明与本次改动无关，不证明代码正确**——可能是测试自身缺陷。
3. **测试依赖生产数据时，CI 与本机会给相反结论**，这类测试的可信度为零。
4. **修 bug 可能引入新风险**（缓存错配就是修 X 合并带出来的），修复后要重新审视新路径。

## 八、仓库完整性（新增，2026-11-25 晚）

### S3【高危】post-commit 后台 agent 带仓库写权限

`scripts/post-commit.sh` 在**每次提交后**后台运行：

```sh
(sleep 1 && deepseek exec --auto "分析最新提交") &
```

`--auto` 意味着一个 LLM 自动执行体，工作目录就是本仓库，**有写权限**。

**实测证据**：本轮 5 次提交，**3 次**在提交后立刻出现
`invalid object ... for 'data/narrative/*.json'`；`git fsck` 显示 51 个
missing blob，指向索引里"从未写出"的对象。恢复方式为
`git add data/narrative && git reset -- data/narrative`（补齐对象后撤销暂存），
修复后 fsck 归零，下一次提交又复现。

**为什么危险**：

1. 一个不可预测的自动执行体 + 仓库写权限，可能 add / commit / reset，行为无法审计
2. 它在本仓工作区里跑，撞上流水线每小时的写盘（`data/narrative/*.json`）时，
   索引里留下指向未写出对象的条目
3. 损坏**不报错、不阻断**，只在下一次 `git commit` 时以 `invalid object` 暴露 ——
   容易被误判为"偶发"

**建议处置**（待主人确认，未擅动）：

| 方案 | 做法 | 代价 |
|---|---|---|
| A | 删除 hook | 不再自动更新 PROJECT_LOG.md |
| B | 保留但去掉 `--auto`（只读分析，输出到 stdout） | 日志仍生成，agent 不改仓库 |
| C | 不动，损坏后手动修 | 每次提交后需补一次索引 |

倾向 **B**。另可考虑：让该 agent 在裸 clone 的镜像目录里跑，与工作区隔离。

**恢复手册**（下次再遇到）：

```bash
git fsck | grep -c "missing blob"          # 确认数量
git add data/narrative && git reset -q -- data/narrative
git fsck | grep -c "missing blob"          # 应为 0
```
