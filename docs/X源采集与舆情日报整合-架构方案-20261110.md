# X 源采集与舆情日报整合 · 架构方案（2026-11-10）

> 定位：现状只有「融合层」，缺「采集层」。本方案把 X 源从一次性试点变成每天稳定供给，并明确职责、契约、调度、降级与灰度。

## 一、结论先行

1. **职责不变**：FA（我）负责采集，monitor 负责融合；monitor 不碰浏览器、不重试、不轮询。
2. **采集通道**：opencli twitter 适配器（已带 x.com 登录态）→ 每只美股 3 切片（top / min_faves:100 / live）→ 写 `data/x_posts/<北京日期>/<TICKER>.json`。
3. **调度**：每天 **06:30** 跑一轮（覆盖前夜美股时段），**19:00** 舆情日报读取；采集硬截止 18:00，超时/失败只降级、不阻塞日报。
4. **范围**：先从 META/GOOGL/RDDT 三只跑 3 天，再扩到配置里的全部 23 只 `.US`。
5. **降级**：登录墙/被限/无数据 → 当天 X 段自动消失，日报纯雪球正常出。
6. **不变量**：X 数据只进 prompt，不写 posts 表、不进统计口径、不进 change_alert。

## 二、现状与缺口

| 层 | 现状 | 缺口 |
|---|---|---|
| 采集（FA） | 2026-11-02 用 Cindy Chrome 做过一次 META 试点，12 条样本 | **没有每日采集器、没有调度、没有状态文件** |
| 契约 | `src/x_sources.py` 定义 v2 字段（metrics_partial/views） | 采集侧未按契约持续产出 |
| 融合（monitor） | 已接 `data/x_posts`、清洗、独立成段、降级 | 无显式配置块、无源覆盖观测 |
| 观测 | 报告里有单标的日志 | 无采集覆盖率、无失败告警 |

> 结论：monitor 侧代码已就绪；缺的是采集层 + 调度 + 观测。

## 三、总体数据流

```
06:30  FA 采集器（opencli twitter search）
        │  每只美股 3 切片 × ≤25 条
        ▼
data/x_posts/<北京日期>/<TICKER>.json  +  _status.json
        │
        ▼
18:30  采集健康检查（覆盖率/登录/字段）
        │  失败只告警，不阻塞
        ▼
19:00  xueqiu-monitor 舆情日报（report_generator）
        │  读一次 → 清洗 → 美股章独立 X 段
        ▼
IMA 笔记 + 飞书卡片 + CSV（结构不变）
```

## 四、数据契约 v2（采集 → monitor）

路径：`xueqiu-monitor/data/x_posts/<YYYY-MM-DD>/<TICKER>.json`，日期=北京日期，TICKER 不带 `.US`。

```json
{
  "ticker": "META",
  "date": "2026-11-10",
  "collected_at": "2026-11-10T06:42:13+08:00",
  "collector": "fa-x-collector/1.0",
  "status": "ok",
  "slices": {
    "top":       {"requested": 25, "returned": 25},
    "min_faves": {"requested": 25, "returned": 21},
    "live":      {"requested": 25, "returned": 25}
  },
  "posts": [
    {
      "tweet_id": "1852...",
      "url": "https://x.com/user/status/1852...",
      "author": "@user",
      "text": "推文正文",
      "lang": "en",
      "slice": "top|min_faves|live",
      "created_at_utc": "2026-11-10T03:12:00Z",
      "metrics": {"like": 12, "reply": 3, "repost": 5, "views": 1800},
      "metrics_partial": false
    }
  ],
  "errors": []
}
```

硬规则：

- `text` 必填，空/纯表情丢弃；`created_at_utc` 保持 UTC 原样。
- 同 URL 跨切片去重，保留互动最高的一条，`slice` 记首次命中。
- `metrics_partial=true`：按钮组渲染不全，数字含义不可信；monitor 直接降权并在 prompt 注明「互动数不可信」，**绝不猜数字位置**。
- `status`：`ok | partial | empty | login_required | failed`（代码口径，`scripts/x_ingest.py` 的 `VALID_STATUS` 为准）。
  - `empty`＝采集跑通但当天确实 0 条；`partial`＝有数据但有切片失败/空返回；`login_required`＝登录态失效；`failed`＝采集本身出错（含被封 `blocked`，ingest 会映射过来）。
  - `_status.json` 汇总当天每只票的状态、条数、各切片计数、错误。
- 原子写：先写 `.tmp` 再 rename；任何一只票失败不影响其他票。
- 空数据也写文件（`posts: []`, `status: "empty"`），让健康检查能区分「采到 0 条」和「没采」。

## 五、采集器设计（FA 侧）

### 5.1 通道（**已改：opencli**）

原方案写的是「Cindy Chrome user-browser」，P0 实测三条路都走不通，已改成 **opencli twitter 适配器**：

| 尝试 | 结果 | 原因 |
|---|---|---|
| 复制用户 Chrome profile + Playwright | ❌ | Chrome 156 启用 app-bound cookie 加密，「Chrome Safe Storage」密钥解出乱码 |
| Playwright 新 profile 人工登录 | ❌ 不采用 | 可行，但要主人再登录一次，且 headless 被 x.com 403 |
| Cindy user-browser 后端 | ❌ | 主人 Chrome 未装 Cindy 扩展（只装了 Material Dark 主题） |
| **opencli twitter** | ✅ | 已带 11-02 试点那个登录态（`whoami` → paradox0504），一条命令 5–6 秒返回结构化 JSON |

因此：
- 采集命令即 `opencli twitter search`，**不保存 cookie、不复制 profile、不碰主人日常 Chrome**。
- 登录态失效时 `whoami` 返回 `logged_in: false` → 写 `login_required`、告警、停止，跑 `opencli twitter login` 恢复。
- 前提：本机 ClashX 代理（`127.0.0.1:7890`）在线——x.com 直连不通。

### 5.2 每只票的动作

```bash
opencli twitter search '$TICKER'               --product top  --limit 25 -f json  # 热门
opencli twitter search '$TICKER min_faves:100' --product top  --limit 25 -f json  # 质量流
opencli twitter search '$TICKER'               --product live --limit 25 -f json  # 最新
```

- 切片间/票间 4–9 秒抖动，串行。
- 每票每天 1 轮；多只票**分多轮**（主人 2026-11-10 确认），3 只以内一轮跑完。
- 失败不重试，记 `partial`/`failed`。
- 字段映射：`id→tweet_id`、`likes→metrics.like`、`views→metrics.views`、`created_at`（`Mon Nov 09 07:03:37 +0000 2026`）→ ISO UTC。
- opencli 不给 reply/repost：有 like 就 `metrics_partial=false`（like 可信），完全没有数字才标 partial。

### 5.3 时间与范围
- 06:30 启动，覆盖前夜美股时段（美股收盘约 05:00 北京）。
- 硬截止 18:00：未完成的票写 `partial`，不阻塞 19:00 日报。
- 第一批：META / GOOGL / RDDT；稳定后扩到 `etc/config.report.json` 的全部 23 只 `.US`。
- 特殊 ticker：`BRK.B.US` 搜索词用 `$BRK.B`，先单测验证；抓不到就标 partial，不猜。

### 5.4 运行形态
- 采集器需要浏览器登录态，**不能是纯 script cron**；作为 Cindy 例行/Agent 任务（06:30）执行，使用 browser 工具。
- 任务书严格限定：只读页面、只写 JSON、不改代码、不发消息，最后输出 `_status.json`。

## 六、融合层设计（monitor 侧）

### 6.1 显式配置
在 `etc/config.report.json` 增加：

```json
"x_source": {
  "enabled": true,
  "root": "data/x_posts",
  "max_posts_per_stock": 75
}
```

回滚：`enabled: false` 即恢复纯雪球，无需改代码。

### 6.2 读取与降级（现有逻辑保留）
- 只对 `.US`；目录/文件缺失、坏 JSON、空数组 → `posts=[]`，不重试、不抛错。
- X 帖独立成段、独立额度，不与雪球混排；标 `[X]`，区分当日/历史。
- 不写 `posts` 表、不进 z-score/温度计、不进 `change_alert`。

### 6.3 观测
- 报告尾部/抬头加一行：`X 源覆盖：N/23 只，M 条`。
- 单标的日志保留「读入 X 条 → 清洗后 Y 条」。
- 采集 `_status.json` 与报告覆盖数不一致时，健康检查告警。

## 七、调度与健康检查

| 时间 | 任务 | 说明 |
|---|---|---|
| 06:30 | X 采集（FA Agent） | 3 切片 × 23 只，硬截止 18:00 |
| 18:30 | 采集健康检查 | 覆盖率、登录、字段校验；缺失只告警 |
| 19:00 | 舆情日报 | 读 `data/x_posts/<今天>`，正常出报 |
| 22:30 | 投递账本日报 | 不涉及 X |

健康检查规则：

- 预期文件数 = 配置里的 `.US` 数量；缺失 >50% → 飞书告警「X 采集大面积缺失」。
- 任一 `status ∈ {login_required, failed}` → 立即告警；`login_required` 提示重新登录 x.com（`opencli twitter login`）。
- `posts` 字段缺 `text`/`url` 比例 >10% → 契约告警。
- 所有告警都**不阻塞** 19:00 日报。

## 八、测试计划

### 8.1 契约层
- `scripts/validate_x_posts.py`：JSON schema 校验（必填、类型、metrics_partial、slice 枚举）。
- 对采集产物逐文件跑；失败列文件与字段。

### 8.2 融合层
- 现有 27 个 X 用例 + 566 全量回归。
- 新增：真实采集 3 只 → 报告 dry-run（不推 IMA/飞书）→ 断言 X 段出现、条数一致、无统计污染（posts 表行数不变、change_alert 无 X）。

### 8.3 降级
- 目录缺失、空目录、坏 JSON、登录失败、单票 0 条：日报均正常出纯雪球版。
- `metrics_partial=true`：prompt 出现「互动数不可信」，不出现猜测数字。

### 8.4 灰度
- 第 1–3 天：META/GOOGL/RDDT 三只，人工看信噪比、条数、报告时长。
- 第 4 天起：扩到 23 只，观察一周；报告时长不得超基线 +10 分钟。
